# ADR-004：失敗工具結果的保留策略

[English](adr-004-failure-retention-strategy.md) | [繁體中文](adr-004-failure-retention-strategy.zh-TW.md)

## 狀態

提案中，刻意延後實作。目前仍維持 ADR-003 的行為：保留一行有意義的錯誤，約 200 個 rune。本文件保存調查、整體資料與對抗式審查結果，讓後續修訂能從證據開始，而不是重新推導。

## 背景

ADR-003 修正了失敗偵測並把摘錄擴大為一行／200 rune，但多行編譯錯誤與 traceback 仍會失去第一個有意義行以後的內容。截斷有隱藏成本：若摘錄不足以判斷根因，讀取端 LLM 會呼叫 `expand`，支付摘錄、工具往返與完整文字三份成本，甚至高於一開始就完整保留。遙測曾發現一個 session 在繼承自己的歷史後，6.5 分鐘內連續呼叫 `expand` 19 次；摘要不足時，實際故障模式是反覆探索，不是一次精準擷取。

### 整體資料（379 個 session、30 天、依 ADR-003 階梯判定 1,194 次失敗）

失敗結果文字長度（字元）：

| p50 | p75 | p90 | p95 | p99 | 最大值 |
|-----|-----|-----|-----|-----|-----|
| 143 | 407 | 1,274 | 2,093 | 11,895 | 26,029 |

- 分布極度右偏：一半失敗在 143 字元內；最長 10%（>1,274）占全部失敗字元的 **68%**（522K/763K），主要是編譯器 dump 與完整測試輸出。
- 每個 session 的失敗很少：中位數 1，p90 為 7；30% session 沒有失敗。
- 「短錯誤完整保留」候選門檻：p75=407 可覆蓋 75%，p90=1,274 可覆蓋 90%，p95=2,093 可覆蓋 95%。暫定建議為約 **1,500 字元**，覆蓋 91–92%。

已知偏差：判定階梯刻意保守，未知形狀會被視為成功，因此本分布只描述「被偵測到」的失敗，真實範圍只會更廣。此外，量測單位是字元／rune，不是 token。

### 通過對抗式審查的設計結論

六項主張交由第二個模型（Codex，xhigh）對抗式審查，結果四項 PARTIAL、兩項 REFUTED。修正後保留下列結論：

1. **兩層保留**：不超過約 1,500 字元的失敗完整保留；更長內容使用 head + tail + signal lines。任何合理門檻都優於固定 200 rune，但延後原因見「決定」。
2. **全域排名，不用堆疊層級**：head、tail、關鍵字 signal lines 在同一個有權重的排名中競爭，並設分類上限與總預算；不能讓前一層先耗光預算。
3. **Signal lines**：比對 `Error:|panic:|FAILED|Caused by:|Traceback|assert`。根因位置依生態不同：Python／Java／測試 runner 常在尾端，Go／Node／編譯器常在前端，因此 head + tail + signal 可同時涵蓋。尚未用人工標註樣本驗證最佳比例，應保守發布，再用 audit 調整。
4. **可自我說明的省略標記**：`(... N lines omitted — <kind>; full text: cc-session expand <session> <tool-id>)`。formatter 必須注入 session ID，短 ID 衝突時改印更長 ID；標記必須誠實說明各分類保留與省略了什麼。
5. **保留預算應依可否重新推導，不只看成功／失敗**：Read 可重新讀目前檔案，通常更有價值；Bash stdout 無論成功或失敗，都是測試 log、API 回應或暫態狀態等歷史證據，只能透過 `expand` 回復。成功／失敗只是粗略代理，真正軸線是讀者能否重建內容。
6. **回饋迴圈**：usage.jsonl 中 `inherit → expand` 的相鄰關係只是截斷失敗的弱代理。要能使用，`expand` 必須記錄 tool-id（目前只記 session ID），並先量測 log 覆蓋率；找不到 caller 時紀錄會被靜默略過。

### 專案路徑救援：已調查並否決

提案是保留提及專案檔案的錯誤行，類似 Sentry 的 in-app frame。理由是新 Claude session 能直接讀 `src/foo.go:42`，卻無法重跑歷史失敗。

對 378 份 transcript、1,169 次失敗的量測否定了「這些行通常藏在 head+tail 漏掉的中段」：

- 長錯誤的路徑行位置近乎均勻：head/middle/tail = 31.5%/35.5%/33.0%，head+tail 已抓到約三分之二。
- 94 個長錯誤中，路徑行只存在於 head+tail 之外的案例為 5–11 個，占全部失敗 0.4–0.9%。
- 被救回的中段行超過一半是雜訊，如帶專案前綴的 node_modules stack frame 或 pnpm banner；抽樣五個只有一個是真訊號。
- 每個長錯誤的路徑行數有長尾，p90=27，仍需逐結果上限。

結論：專用路徑比對層需要專案根目錄解析、`cleanCwdPaths` 互動、路徑邊界／symlink 處理，以及補足 `ToolResult` 缺少 cwd 等子系統，卻只增加不到 1% 覆蓋且一半是雜訊，因此不採用。窄化的 `path:line` signal regex 也一併否決。若未來重啟，價值集中於排除 node_modules 後的「相對路徑 + 行號」panic／traceback 形式。

## 決定

**延後實作，維持 ADR-003 不變。**

兩層設計已有證據，但支援量測尚未就緒。只有先加入 expand tool-id log 與覆蓋率量測，才能把一次性的門檻猜測變成可調整系統；在缺少這些工具時發布，正好會對「截斷造成的 expand」這個核心指標失明。調查成本已保存於本文件，日後可直接由此開始實作。

### 重新評估觸發條件

- inherit 後再次觀察到 6.5 分鐘 19 次之類的 burst-expand。
- `expand` 開始記錄 tool ID，回饋迴圈前提成立。
- 使用者具體回報一行摘錄看不到根因。

### 未來實作必須保留的限制

- 失敗統計有 false-negative 偏差。
- Rune 不等於 token，門檻最終應以 token 驗證。
- 編譯診斷、stack trace、assertion 可能需要不同策略；通用 signal regex 可能留下錯行、刪掉相鄰關鍵行。
- 完整保留的短錯誤可能包含 secret、環境變數或 API 回應，應評估遮罩處理。
